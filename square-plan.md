## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter, built with an object initializer using that record's own property names. Never use flat arguments. An operation with no inputs (`ListLocations`) takes none.
> ⚠ **Write every SDK type fully qualified, with the namespace its own source path implies**: `src/Square/Models/X.cs` → `Square.Models.X`, `src/Square/Models/Enums/X.cs` → `Square.Models.Enums.X`, `src/Square/Requests/<Ctl>/X.cs` → `Square.Requests.<Ctl>.X`, `src/Square/Core/Exceptions` → `Square.Core.Exceptions`, `src/Square/Core/ErrorResponse` → `Square.Core.ErrorResponse`, `src/Square/Core/Models` → `Square.Core.Models`, `src/Square/Core/Configuration` → `Square.Core.Configuration`, `src/Square/Core/Hooks` → `Square.Core.Hooks`, `src/Square/Servers` → `Square.Servers`. Take the namespace from the path the map gives for THAT type, never from a neighbouring type. **Enums are in `Square.Models.Enums`, which `using Square.Models;` does not import.**

**Signature convention.** Every method below is `Task<TResponse> Method(TRequest request, Square.Core.RequestOptions? requestOptions = null, System.Threading.CancellationToken cancellationToken = default)`. The rows write the trailing two parameters as `…`. Auth on every row: `options.BearerAuth`. Error on every row: **Case B**, `Square.Core.Exceptions.ApiException<Square.Core.ErrorResponse.RawError>` (map: *0 Case A, 305 Case B*). Pagination on every row: **none** (no row carries a Pagination bullet), so the SDK never follows a `cursor`.

## 3. Trap notes

- **S0–S10 (every step).** 3.0.0 moved many fields from `string` to open enums that live in a namespace `using Square.Models;` does not import. In `SquarePaymentMethod.cs` (which imports `Nop.Core.Domain.Directory` and `Nop.Core.Domain.Common`), unqualified `Currency`, `Country` or `Address` becomes ambiguous (CS0104). Inside `namespace Nop.Plugin.Payments.Square…`, a bare `Square.` resolves to the plugin namespace. **MUST load bench-square:dotnet-models**
- **S2, S4, S6, S7.** Comparing an open enum with string literals: some forms compile and behave (`==`/`!=`), some compile and crash on null (implicit conversion to `string`), and some don't compile (`case`/`is` patterns). Picking a form by "whatever compiles" brings back a null crash or a silent mismatch. **MUST load bench-square:dotnet-models**
- **S3, S5, S7.** Assigning a currency or country code from nopCommerce data to an enum field: what happens to a code the SDK does not declare is a model-shape question, and it decides whether a payment is sent without a currency. **MUST load bench-square:dotnet-models**
- **S4.** ListCards is capped per call and the SDK does not page it. Omitting `CustomerId` changes whose cards come back. Both silently change what the shopper sees on checkout and on the Saved Cards page. **MUST load bench-square:dotnet-calling-endpoints** and **bench-square:dotnet-configuration-resilience** (pagination)
- **S5.** A field the 3.0.0 model no longer declares can only travel in the extension-data bag. Whether its wire name and JSON type come out exactly as before depends on how the bag serializes values. **MUST load bench-square:dotnet-models**
- **S2, S7.** Required members on response models (`Error.Category/Code`, `Refund.*`, `Tender.Type`, `PaymentRefund.Id/AmountMoney`, `CatalogObject.Type/Id`) turn a drifted body into an exception from a different family than a provider refusal. The refusal-vs-failure split in `RefusalOrThrowAsync` depends on which family arrives. **MUST load bench-square:dotnet-error-handling**
- **S1.** Leaving `BearerAuth` null silently switches the credential source. **MUST load bench-square:dotnet-authentication**
- **S1.** What `RetryOptions.Timeout` bounds, as opposed to `HttpClient.Timeout`, and which verbs the default policy resends, decide the real latency budget of a checkout. **MUST load bench-square:dotnet-configuration-resilience**
- **S1.** The factory builds a client per call over `IHttpClientFactory`. Who owns and disposes the `HttpClient` affects connection reuse. **MUST load bench-square:dotnet-client-initialization**
- **S9.** NUnit `Is.EqualTo("ADJUSTMENT")` against an enum-typed property compiles but fails at run time, because record equality never matches a string. The stub serializes SDK models with default `JsonSerializer` options, and request bodies are read back the same way, so extension-bag keys show up in `AdditionalProperties`, not as properties. **MUST load bench-square:dotnet-testing**

## 6. Assumptions & Blockers

- **A-1 (assumption).** The tests in `src/Tests/Nop.Plugin.Payments.Square.Tests` may be edited to match 3.0.0 types, because they build SDK models from strings. The saved-cards test must stub `GET /v2/cards` with a `Square.Models.ListCardsResponse` instead of `Customer.Cards`. The assertions on `Type`, `FromState`, `ToState`, `ProductType` and `PricingType` must compare against enum members or `.Value`, and the catalog test must read the availability flags from `ItemData.AdditionalProperties`. What the tests check stays the same.
- **A-2 (behaviour 3.0.0 may not keep; report to the user).** `Square.Models.CatalogItem` in 3.0.0 does not declare `available_online`, `available_for_pickup` or `available_electronically`. To keep the request on the wire unchanged, the plan sends them through `CatalogItem.AdditionalProperties` (C-7), under those wire names, as JSON booleans, the same way the code already sends `integration_id`. **UNVERIFIED:** only live traffic can show whether Square still honours fields the 3.0.0 spec no longer declares. If it does not, catalog items lose their online, pickup and electronic availability flags. The alternative is to drop the three flags, which is a visible behaviour change.
- **A-3 (behaviour change forced by 3.0.0; report to the user).** `Customer.cards` is gone, so saved cards come from `Cards.ListCards(CustomerId)`, which by default returns enabled cards only (the code already filtered `Enabled != false`). Two differences follow. (a) Today a Square customer id that no longer exists fails `RetrieveCustomer` with a 404, so the page shows its error message. With ListCards, the response for an unknown `customer_id` is UNVERIFIED (likely an empty list). (b) Whether ListCards returns exactly the cards that `customer.cards` used to return is UNVERIFIED.
- **A-4 (decided).** `Money.Currency` and `Address.Country` are now enums with no public factory (C-8). The proposed handling: a currency code that `Currency.TryGetKnownValue` does not resolve throws `NopException`, because Square would refuse a money amount without a currency. A country that does not resolve becomes `null` and is omitted, which matches the code's existing null path. Today the code sends any string. The 3.0.0 enums cover 183 currencies and 250 countries, and the code already restricts currency to ISO codes (`CheckSupportCurrency`). **Decision (implemented):** `Services/SquareCodes.ToCurrency` (trim + upper-case, `Currency.TryGetKnownValue`, else `NopException`) and `SquareCodes.ToCountry` (same, else `null`), used by `SquarePaymentMethod` (address + both `Money` builds), `SquareCatalogService.UpsertProductAsync` and `LegacyTransactionService.RefundAsync`.
- **A-5 (assumption).** `Error.Category` and `Error.Code` are `required` in 3.0.0. An error body that lacks either makes `ReadAsJson` throw `JsonException`, which `ReadErrorDetails` already catches, so the exception message is shown instead. No code change is needed beyond the `Code` switch.
- **A-6 (main agent to confirm with the user).** Three CROSS-OPERATION INVARIANTS are not enforced by the current code, and the workflow requires the check. These gaps exist today; 3.0.0 did not introduce them. They are: (1) a stored-card `SourceId` that must belong to the customer, (2) the location saved in Configure (POST) that must be in `GetActiveLocationsAsync`, and (3) the inventory location ids that must be in `ListLocations`. Adding the checks tightens behaviour (a forged stored-card id or a mistyped warehouse location is refused before the call). The user asked for unchanged behaviour, so confirm before adding them. **Decision:** not added in this upgrade — they are pre-existing gaps unrelated to 3.0.0 and the task requires behaviour to stay the same; reported to the user.
- **A-7 (assumption).** PR-1 extends the existing blank-token check to production. Without it, a store with no token would, under 3.0.0, call Square with whatever `SQUARE_BEARER_AUTH` holds in the process environment. With the check, it fails before the call, as it already does in sandbox.
- **A-8 (assumption).** The legacy refund keeps using `Tender.Id` as the payment id. The 3.0.0 doc on `Tender.id` says "It is the associated payment ID." `Tender.PaymentId` exists too, but is "only present for payments created with the v2 Payments API", so it would not cover legacy tenders.
- **B-1 (Blocker, pre-existing).** DUPLICATE CLAIMS: every write a caller can trigger twice (checkout double-submit → CreatePayment; concurrent admin capture, void or refund; repeated sync events) has no claim store this plugin owns with a key that refuses a second caller before the SDK call. Building one means a new entity and schema migration, which is beyond a version bump with minimal changes. The upgrade leaves today's behaviour as it is (each write's own idempotency key, PR-5). The user must decide whether to add claims. **Decision:** unchanged by this upgrade; reported to the user.
- **B-2 (Blocker, pre-existing).** UNKNOWN OUTCOMES: today the code reports a connection failure after a write as a failure. In the payment workflow that is `SquarePaymentManager.RefusalOrThrowAsync` → `SquareServiceException`; elsewhere the exception propagates. It does not settle the outcome. Settling (for example `CancelPaymentByIdempotencyKey` after a failed CreatePayment) changes behaviour, which the user asked to keep. The rows above name the re-read operations 3.0.0 offers. **Decision:** not implemented in this upgrade (behaviour kept); every row's code/test cells read "not implemented — B-2"; reported to the user.
