## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, copied verbatim.** An operation that takes input takes ONE request record as its first parameter. Build it with an object initializer using the record's own property names, never flat arguments. An operation with no inputs (`ListLocations`) takes no record.
> ⚠ **Write every SDK type fully qualified, with the namespace implied by its own source path** as the map gives it for THAT type: `src/Square/Models/X.cs` → `Square.Models.X`; `src/Square/Models/Enums/X.cs` → `Square.Models.Enums.X`; `src/Square/Requests/<Ctl>/X.cs` → `Square.Requests.<Ctl>.X`; `src/Square/Core/Exceptions/X.cs` → `Square.Core.Exceptions.X`; `src/Square/Core/ErrorResponse/RawError.cs` → `Square.Core.ErrorResponse.RawError`; `src/Square/Core/Models/AdditionalProperties.cs` → `Square.Core.Models.AdditionalProperties`; `src/Square/Core/Configuration/*` → `Square.Core.Configuration`; `src/Square/Core/Hooks/SdkHook.cs` → `Square.Core.Hooks`; `src/Square/Servers/ServerEnvironment.cs` → `Square.Servers`. Do not assume an enum sits beside its model: **enums are in `Square.Models.Enums`, which `using Square.Models;` does not import.**

Common to every row (map index defaults): auth `options.BearerAuth`. Throw-only, with no `…Result` siblings. **Case B**: `ApiException<Square.Core.ErrorResponse.RawError>` with `.Error.StatusCode`, `.ReadAsBytes()`, `.ReadAsString()`, `.ReadAsJson<T>()` (plain `JsonSerializer.Deserialize<T>`, no options). Server group `Default`. **No SDK pagination** on any operation here: the cursor fields are plain members. Every signature also takes `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`, which are left out of the table below.

### 2c. Enums: every one is a `sealed record : OpenStringEnum<T>` in `Square.Models.Enums`

Mechanics, from `src/Square/Core/Enum/TypedEnum.cs` and `StringEnum.cs`:
- Members are static fields such as `LocationStatus.Active`.
- There is no public constructor and no string-to-enum conversion. The only way to resolve a raw string is `T.TryGetKnownValue(string?, out T?)`, which returns false for an unknown value, so the SDK cannot build an unknown value on the request side.
- `implicit operator string(TypedEnum)` returns `.Value`. It throws a NullReferenceException when the enum reference is null.
- `operator ==` / `!=` are defined against `string`. `.Is(string)`, `.Value` and `.IsKnownValue()` exist. `ToString()` returns the wire value.
- Record equality applies, so `Equals(object)` against a `string` is **false**.
- An unknown wire value deserializes as an instance that is not among the known members, so it is preserved.
- The generated `Match(…, otherwise)` exists.

## 6. Assumptions & Blockers

**Blockers / behaviour 3.0.0 cannot keep**

- **B1: duplicate claims have no store.** Writes a caller can trigger twice include `CreatePayment` (double checkout submit), `RefundPayment` (admin refunds twice), `CreateCustomer` and `CreateCard` (two concurrent checkouts for the same customer), `UpsertCatalogObject` / `BatchChangeInventory` (repeated product and stock events), and `CreateCustomerCustomAttributeDefinition`. The plugin owns no table. It persists only through nopCommerce `GenericAttribute` (`IGenericAttributeService`), which is a read-then-upsert. Its only index (`IX_GenericAttribute_EntityId_and_KeyGroup`, `Libraries/Nop.Data/Migrations/Installation/Indexes.cs`) is non-unique, so it refuses no second claim. Adding a claim table means a schema migration, which is out of scope for a version upgrade. This is **not addressed** by the upgrade and needs the user's decision. The behaviour is the same as at 1.2.0.
- **B2: catalog availability flags removed.** The 3.0.0 `CatalogItem` (`src/Square/Models/CatalogItem.cs`) declares no `available_online`, `available_for_pickup` or `available_electronically`. Today's `UpsertProductAsync` sets all three from `Published` / `IsDownload`. The closest 3.0.0 field is `Channels (channels): IReadOnlyList<string>?` ("IDs representing channels, such as a Square Online site"), and the plugin has no channel ids. Options: (a) drop the three fields, which is a behaviour change because products are no longer flagged online, pickup or electronic; or (b) send them as `CatalogItem.AdditionalProperties` entries under their old wire names, the way `integration_id` is sent today. That keeps the request body identical, but whether Square still honours fields its 3.0.0 spec no longer declares is `UNVERIFIED`. The `SquareCatalogServiceTests.UpsertProduct_PublishesTheItemOnline` assertion on `ItemData.AvailableOnline` must change either way. **Decided: (a).** `SquareCatalogService.UpsertProductAsync` no longer sends the three flags. Sending wire fields the 3.0.0 contract no longer declares would be guessing, so this is reported as a behaviour change. The test assertion on `AvailableOnline` was replaced with an assertion on `CatalogObject.Type`.
- **B3: saved cards are no longer on `Customer`.** 3.0.0 `Customer` has no `cards`. `GetSavedCardsAsync` must call `Cards.ListCards(CustomerId)` and walk its cursor (max 25 per page). Possible behaviour change (`UNVERIFIED`): for a customer id Square no longer knows, the old `RetrieveCustomer` threw a 404 `ApiException`, while `ListCards` may return an empty list. `PaymentSquareController.SavedCards` and `PaymentSquareViewComponent` would then show "no cards" instead of the error message. **Implemented** in `SquareCardService.GetSavedCardsAsync`, which uses `ListCardsOperationRequest { CustomerId, Cursor }` and leaves `IncludeDisabled` at false. The `Enabled != false` filter is kept.

**Assumptions**

- **A1:** The 1.2.0 contract is inferred from the existing code, which compiled at 1.2.0. Every "delta" cell compares that use with the 3.0.0 source. No 1.2.0 source was read.
- **A2 (major, ask the user):** the skill's UNKNOWN OUTCOMES, cross-operation and duplicate-claim rules call for reconciliation and validation code that the 1.2.0-era plugin never had (re-sending with the same idempotency key, `GetPayment` re-reads, keeping the `BatchChangeInventory` key across retries, setting `CreateCustomerRequest.IdempotencyKey`). The user asked for minimal changes with behaviour kept the same. **Decided:** implement only what the upgrade forces (steps 1–11). These rows are reported as known pre-existing gaps.
- **A3 (major, ask the user):** three invariants in 2e are not enforced today: the stored-card id at checkout, the Configure `LocationId`, and the warehouse `SquareLocationId`. Closing them is new validation, not an upgrade necessity. **Decided:** not added, same as A2. The stored-card id is still checked only through `GetCustomerAsync`, and `DisableCardAsync` still checks membership through `GetSavedCardsAsync`, which now reads all pages.
- **A4:** keep the factory's sandbox-only token check (behaviour). Coalescing a `null` production token to `string.Empty` was considered. **Decided:** not changed. `SquareClientFactory.CreateAsync` is unchanged apart from `ServerEnvironment.Sandbox`, and the env-var fallback is reported as a note.
- **A5: enum conversion from nopCommerce strings.**
  - `Money.Currency`: `Currency.TryGetKnownValue(currency.CurrencyCode.ToUpperInvariant(), …)`. A code the SDK does not know (outside its 183 ISO 4217 members) cannot be sent. The existing `CheckSupportCurrency` gate makes this rare. On failure, throw the same `NopException("The {code} currency is not supported by the Square")` the plugin already uses. **Implemented** as `SquareValues.ToCurrency` (`Services/SquareValues.cs`), used by `SquarePaymentMethod` (payment and refund `Money`), `SquareCatalogService` and `LegacyTransactionService.RefundAsync`.
  - `Address.Country`: `Country.TryGetKnownValue(TwoLetterIsoCode)`. Fall back to `null`, which matches today's `null` for an unrecognised region. **Implemented** as `SquareValues.ToCountry`, used in `SquarePaymentMethod.CreatePaymentRequestAsync`.
- **A6:** `Payment.Status` and `PaymentRefund.Status` are still `string?` in 3.0.0. `SquarePaymentDefaults.Status.PAYMENT_*` / `REFUND_*` and `GetPaymentStatus(string)` stay unchanged. `LOCATION_ACTIVE` / `LOCATION_PROCESSING` become comparisons against `LocationStatus.Active` / `LocationCapability.CreditCardProcessing` (or their `.Value`).
- **A7:** the `CreatePaymentRequestExtensions.WithIntegrationId` mechanism is unchanged in 3.0.0 (`[JsonExtensionData] AdditionalProperties`, `init`, `Set`). A test asserting `integration_id` in the outgoing `POST /v2/payments` body is recommended but optional (tests change only where the API changed).
- **A8:** `Refund` (legacy) now requires `id`, `location_id`, `tender_id`, `reason`, `amount_money` and `status`. A legacy transaction whose refund lacks one now fails as a whole (`ResponseDeserializationException`, not a `NopException`). It propagates out of `LegacyTransactionService` exactly as an `ApiException` does today. `UNVERIFIED` whether Square ever omits `reason`.
- **A9:** `StubSquare.cs` needs no change. In `SquarePluginTests.cs`, every fixture touches a changed member (enum initializers or assertions, `Customer.Cards`, `CatalogItem.AvailableOnline`), so all five need edits limited to those members.
