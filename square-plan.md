## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter (an operation with no inputs, like `ListLocations`, takes none). Build it with an object initializer using the record's own property names, never flat arguments. Every operation also takes `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`.
> ⚠ **Every SDK type is written fully qualified, with the namespace its source path implies.** Take the path the map gives for THAT type, never the folder a neighbouring type sits in: `src/Square/Requests/<Controller>/` → `Square.Requests.<Controller>`, `src/Square/Models/` → `Square.Models`, `src/Square/Models/Enums/` → `Square.Models.Enums`, `src/Square/Core/Exceptions/` → `Square.Core.Exceptions`, `src/Square/Core/ErrorResponse/` → `Square.Core.ErrorResponse`.

Defaults that hold for every row (sdk-map.md defaults table): throw-only, no `…Result` variants, **Case B** (`ApiException<RawError>`: `StatusCode`, `ReadAsBytes()`, `ReadAsString()`, `ReadAsJson<T>()`), **no SDK pagination**, server group `Default`, Auth `options.BearerAuth`. The map lists 0 Case A operations in this SDK.

## 6. Assumptions & Blockers

**Blockers:** none. The map and the 4.0.0 source cover every use. No call the plan keeps is expected to be rejected by the provider because of the upgrade.

**Assumptions:**

- **A1.** The task is a version upgrade. The only required code changes are M1–M3 (renames, which fail to compile) and M4 (`Refund.TenderId` now optional, which still compiles). Every other use was checked against the 4.0.0 file and the 3.0.0→4.0.0 diff of that file, and is unchanged (2.2).
- **A2 (M4 decision).** DECIDED and implemented in `LegacyTransactionService.GetRefundableBalancesAsync` (guard before the balance arithmetic): an **active** legacy refund (`Pending`/`Approved`) with `TenderId == null` makes `GetRefundableBalancesAsync` throw a `NopException` naming the transaction, so no refund is issued. Inactive refunds with null `TenderId` are ignored, as today. This keeps the 3.0.0 outcome (the call failed, nothing was refunded). The visible difference is the exception type: it is now a `NopException`, so `SquarePaymentMethod.RefundAsync` returns it as a `RefundPaymentResult` error instead of an unhandled `ResponseDeserializationException`. Report this in the summary as a 4.0.0 behaviour change the code cannot keep identically. Add one test in `LegacyTransactionServiceTests` (it calls `RetrieveTransaction`, the part that changed); change no other test.
- **A3.** The pre-existing gaps above are recorded, not fixed: no duplicate claims, no unknown-outcome settlement, no stored-card / location membership check before `CreatePayment`, and the unread inventory-count cursor. Fixing them would change behaviour, which the task forbids for this upgrade. None of them is caused or changed by 4.0.0: `src/Square/Core` and every affected model are identical between the versions.
- **A4.** Credential handling stays as it is: a null production token falls back to `SQUARE_BEARER_AUTH`, and a blank one is sent blank. The 4.0.0 runtime is unchanged here, and changing it would change behaviour.
- **A5.** The 4.0.0 `ErrorCode` additions (`ReaderDeclined`, `RefundErrorPaymentNeedsCompletion`, `OrderUnpaidNotReturnable`) need no mapping. `DescribeError` already falls back to Square's `detail` for any unmapped code.
- **A6.** The test project has no direct `ApimaticBench.Square` reference; it gets 4.0.0 through `ProjectReference`. No existing test uses a renamed record, so existing tests need no edits.
