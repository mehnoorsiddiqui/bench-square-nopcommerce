## 2. CONTRACT SHEET (3.0.0)

> ⚠ **Signatures are generated code, verbatim.** Every operation that takes input takes ONE request record as its first parameter (`ListLocations` takes none). Build it with an object initializer that uses the record's own property names, never flat arguments. Every call also takes `RequestOptions? requestOptions = null, CancellationToken cancellationToken = default`.
>
> ⚠ **Every SDK type is written fully qualified, with the namespace its source path implies, taken from the path the map gives for THAT type.** `src/Square/Models/X.cs` is `Square.Models.X`. `src/Square/Models/Enums/X.cs` is `Square.Models.Enums.X`. `src/Square/Requests/<Controller>/X.cs` is `Square.Requests.<Controller>.X`. `RawError` is `Square.Core.ErrorResponse.RawError`. `ApiException<T>`, `ResponseDeserializationException` and `SdkException` are `Square.Core.Exceptions.*`. `ServerEnvironment` is `Square.Servers.ServerEnvironment`. `RetryOptions` and `LoggingOptions` are `Square.Core.Configuration.*`. `SdkHook` is `Square.Core.Hooks.SdkHook`. `AdditionalProperties` is `Square.Core.Models.AdditionalProperties`.

**Common to every row:** throw-only, with no `…Result` variant. **Error Case B for every operation**: `Square.Core.Exceptions.ApiException<Square.Core.ErrorResponse.RawError>`, whose `.Error` exposes `StatusCode: HttpStatusCode` · `ReadAsBytes()` · `ReadAsString()` · `ReadAsJson<T>()`. The map counts 0 Case-A operations out of 305. There is no `Pageable`, server group `Default` and auth `options.BearerAuth`. Source for these facts: `sdk-map.md` (error model, defaults table, Servers & auth).

**Hazard row (verbatim):** a body that does not match its declared type surfaces as `ResponseDeserializationException`. That covers a drifted or malformed **2xx** response (a missing `required` member), and a **non-2xx** body that does not match its operation's generated `{Operation}Error` shape. ## 5. PRODUCTION READINESS

| # | Concern | Decision |
| --- | --- | --- |
| 1 | Credential fail-fast | The credential is the per-store `SquarePaymentSettings.AccessToken` (via `ISettingService`). It is editable at runtime and read on every `SquareClientFactory.CreateAsync`, so host-start fail-fast is not possible. The fail-fast point is `CreateAsync`. Today it throws only when sandbox and empty. **Decision: also throw `NopException` in production when the token is null or whitespace.** Never pass null to `BearerAuth`, because null arms the `SQUARE_BEARER_AUTH` env fallback (§2.5). This is a single-part credential. |
| 2 | Secret sourcing & rotation | The source is the nop settings table, per store. `RenewAccessTokenTask` rotates it. There is no singleton options object: the client is built per call from freshly loaded settings, so a rotated token takes effect on the next call without a restart. Keep it this way. |
| 3 | Total timeout budget | The knobs stay as they are: `HttpClient.Timeout = 30s` (`NopStartup`) and `RetryOptions.Timeout = 30s` on top of `Default()` (`MaxRetries=3`, 1s exponential ×2 + ≤500ms jitter, `Retry-After` honoured and capped at 60s). The plugin passes no `CancellationToken`. **Budget:** a POST (every write) gets one attempt, ≤ **30s**. A GET (`RetrieveLocation`, `RetrieveCustomer`, `ListCards` per page, `RetrieveTransaction`, `RetrieveInventoryTransfer`, custom-attribute reads) ends at ≈30s when `HttpClient.Timeout` fires, because that is not retried. On retryable statuses it can take up to 4 × 30s + 1s + 2s + 4s + 3 × 0.5s ≈ **128.5s**, or ≈ 300s if Square sends a large `Retry-After` on each attempt. These values are unchanged from the 1.2.0 code. Lowering them would be a behaviour change outside this upgrade, so they are kept. |
| 4 | Write-retry ownership | Every in-scope write is a POST (O4, O5, O7–O13, O15, O16, O18, O20 (a read sent as POST), O21, O22). POST is not in `Default().HttpMethodsToRetry`, so the SDK never resends them. The plugin owns resend decisions: today only `SquarePaymentMethod.RefundAsync` re-sends a PENDING refund with the same `IdempotencyKey`. No other write is retried. Keep it so. |

| 6 | Observability | No change. Failures go to the nop `ILogger` at Error (`CatchExceptionAsync`, sync consumers) or Warning (no active location, customer-link failure). ## 6. Assumptions & Blockers

**Blockers**

- **B1. `CatalogItem` lost `AvailableOnline`, `AvailableForPickup` and `AvailableElectronically` in 3.0.0** (`src/Square/Models/CatalogItem.cs` has no such members; the only related member is `channels`, which is documented as read-only). `SquareCatalogService.UpsertProductAsync` sets all three from `Published`/`IsDownload`, and the catalog test asserts `AvailableOnline`. Behaviour cannot be kept through the typed model. The user must choose:
  - (a) Drop them. Square then applies its own defaults for online, pickup and electronic availability, which is a behaviour change to flag.
  - (b) Send them through `CatalogItem.AdditionalProperties` (`[JsonExtensionData]`) under the wire names `available_online`, `available_for_pickup`, `available_electronically`. The code already uses this pattern for `integration_id`. Those wire names are **not in the 3.0.0 map**, so whether Square still accepts them is UNVERIFIED.

  Either way the test assert changes.

  **Decision (implemented):** (a) drop them. 3.0.0 has no such members and the map does not name the wire fields, so sending them through extension data would be a guess. `SquareCatalogService.UpsertProductAsync` no longer sends availability; `Published`/`IsDownload` stay on `CatalogProductInfo` but no longer reach Square. Behaviour change, reported in the summary. The catalog test asserts `Type`/`ProductType`/`PricingType` instead of `AvailableOnline`.
- **B2. Saved cards must change endpoint.** `Square.Models.Customer` has no `cards` in 3.0.0, so `SquareCardService.GetSavedCardsAsync` must call `Cards.ListCards` (`GET /v2/cards?customer_id=…`, max 25 per page, cursor). This is a new SDK call and a different Square endpoint. The visible result (enabled cards of that customer) should be the same, but the change cannot be avoided and should be reported to the user. The card-owner check in `DisableCardAsync` follows automatically. **Implemented** in `SquareCardService.GetSavedCardsAsync` (cursor walk, `CustomerId` always set because an empty id returns early).
- **B3. No claim store for duplicate prevention.** Each of these writes can be triggered twice by a caller:
  - CreatePayment (double-submit at checkout)
  - CreateCustomer and CreateCard (first save-card checkout)
  - RefundPayment (admin double-click)
  - Complete/CancelPayment and Capture/VoidTransaction
  - DisableCard
  - UpsertCatalogObject and BatchDeleteCatalogObjects (product save events)
  - BatchChangeInventory (stock history insert)
  - the custom-attribute writes

  The plugin keeps records in nop generic attributes (`IGenericAttributeService`), and those rows have an identity key, so nothing refuses a second claim. A refusing claim needs a new table or a unique index, which is a schema change. The 1.2.0 code has no claims either. **Decision: left out of scope (unchanged from 1.2.0) and reported.**

**Assumptions**

- **A1.** `ServerEnvironment.Environment2` (in the 1.2.0 code) meant sandbox, because the code selects it on `UseSandbox`. Mapping it to `ServerEnvironment.Sandbox` keeps behaviour.
- **A2. Defaults that cannot be compared.** No 1.2.0 source or release notes are available. The code overrides only `Timeout` and the logger, so 3.0.0's `RetryOptions.Default()` values (§2.5) apply unchanged. If 1.2.0's defaults differed (count, statuses, verbs), retry behaviour changes silently (UNVERIFIED). Likewise, whether 1.2.0 already used a null-`BearerAuth` → `SQUARE_BEARER_AUTH` fallback is not visible. §5 row 1 removes the dependence on that fallback.
- **A3. Value mapping for the new enums.**
  - Currency (implemented as `SquareCodes.ToCurrency`, which upper-cases the code first): `Square.Models.Enums.Currency.TryGetKnownValue(currency.CurrencyCode)`. If the value is unknown, throw `NopException` with the same "currency is not supported by the Square" wording that `CheckSupportCurrency` uses, rather than sending a payment with no currency. This only adds an explicit failure where Square would reject anyway.
  - Country (implemented as `SquareCodes.ToCountry`): `Country.TryGetKnownValue(...)`, with null when unknown. This matches today's null-on-invalid branch.
  - Legacy `LegacyTenderBalance.Currency`: `tender.AmountMoney?.Currency?.Value`, because an implicit conversion on null throws.
  - Card brand and type switches: switch on `card.CardBrand?.Value` / `card.CardType?.Value`, or on the enum members. Display text is unchanged.
- **A4. Behaviour additions the skill's tables call for, beyond a minimal upgrade.** These are:
  - the CreatePayment stored-card membership check (§2.3)
  - the inventory location membership check (§2.3)
  - the production empty-token guard (§5 row 1)
  - the counts cursor walk (PAGED READS)
  - every UNKNOWN OUTCOMES row

  The ListCards cursor walk is required to keep behaviour, so it is not in this list. The user asked to keep changes minimal and behaviour the same. **The main agent should confirm these with the user before implementing them.** **Decision:** implemented the empty-token guard (`SquareClientFactory.CreateAsync` throws `NopException` for an empty `AccessToken`, so `BearerAuth` is never null and `SQUARE_BEARER_AUTH` is never read) and the ListCards cursor walk. The counts walk is not needed (see PAGED READS). The stored-card and inventory-location membership checks and the UNKNOWN OUTCOMES re-reads are not implemented (pre-existing gaps, not caused by 3.0.0) and are reported as recommendations.
- **A5.** `Error.Category` and `Error.Code` are now `required`. A Square error entry missing either one makes `ReadAsJson<SquareErrorBody>` throw `JsonException`, which is already caught, so the message falls back to the exception text. Behaviour is otherwise unchanged. `DescribeError` must compare `error.Code` against `ErrorCode.*` members (or `.Value`), not string constant patterns.
- **A6.** `PaymentRefund.Id`/`AmountMoney`, `Refund.*` and `Tender.Type` are now `required`. A Square 2xx body missing any of them throws `ResponseDeserializationException`. `RefundPaymentAsync` already classifies that as a Square failure (`SquareServiceException`). `LegacyTransactionService` lets it propagate, and `SquarePaymentMethod.RefundAsync` catches only `NopException` on the legacy path, so a deserialization failure there would escape as an exception rather than an error result. Decision: not widened. In 1.2.0 an `ApiException<RawError>` on that path also escaped the `NopException` catch, so the error contract of `SquarePaymentMethod.RefundAsync` is kept as it was; reported in the summary.
- **A7.** The tests will be edited only for the SDK changes in §2.6. The `StubSquare` route key for saved cards becomes `"GET /v2/cards"`.
