## 2. CONTRACT SHEET

> ⚠ **Signatures are generated code, verbatim.** Each operation that takes input takes ONE request record as its first parameter (an operation with no inputs — `ListLocations` — takes none), built with an object initializer whose property names are the record's own; never flat arguments.
> ⚠ **Every SDK type is written fully-qualified with the namespace its source path implies**, taken from the path the map gives for THAT type, never from where a neighbouring type sits: `src/Square/Models/X.cs` → `Square.Models.X`; `src/Square/Models/Enums/X.cs` → `Square.Models.Enums.X`; `src/Square/Requests/<Ctl>/X.cs` → `Square.Requests.<Ctl>.X`; `Core/Exceptions` → `Square.Core.Exceptions`; `Core/ErrorResponse` → `Square.Core.ErrorResponse`; `Core/Models` → `Square.Core.Models`; `Core/Configuration` → `Square.Core.Configuration`; `Core/Hooks` → `Square.Core.Hooks`; `Servers` → `Square.Servers`. Inside `namespace Nop.Plugin.Payments.Square…` a bare `Square.` resolves to the plugin namespace — qualify in code bodies as `global::Square.…` (the code already does this for `SquareClient`).

Common to every row: **Auth** `options.BearerAuth`; **Error** `ApiException<RawError>` — **Case B** (accessors `StatusCode`, `ReadAsBytes()`, `ReadAsString()`, `ReadAsJson<T>()`); server group `Default`; every response envelope also carries `Errors: IReadOnlyList<Square.Models.Error>?` (`errors`). Signature tail on every row is `(…, RequestOptions? requestOptions = null, CancellationToken cancellationToken = default)`.

## 6. Assumptions & Blockers

**Blockers (need the user's answer):**

- **B1 — DECIDED: keep 1.2.0 behaviour, no claims added (dependency upgrade only).** Duplicate claims vs. "keep changes minimal and behaviour the same." The workflow requires a store-enforced claim before every write a caller can trigger twice (12 rows above). The 1.2.0 plugin keeps none, and I have read no table/key in this codebase that would refuse a second claim. Adding one is new persistence and new behaviour, outside a dependency upgrade. Proposed: keep 1.2.0 behaviour (no new claims) and record the rows as "not in scope of the upgrade", unless the user wants them added.
- **B2 — DECIDED: keep 1.2.0 behaviour, no reconciliation added.** Unknown outcomes vs. minimal change. 1.2.0 reports connection/5xx failures as `SquareServiceException` (`RefusalOrThrowAsync`) instead of settling them. The 3.0.0 map offers settle paths (e.g. `CancelPaymentByIdempotencyKey`), listed above. Proposed: keep 1.2.0 behaviour for this upgrade unless the user asks for reconciliation.

**Major assumptions (surface to the user):**

- **A1 — `CatalogItem.AvailableOnline/AvailableForPickup/AvailableElectronically` were removed in 3.0.0 with no replacement member** (`src/Square/Models/CatalogItem.cs`; `CatalogItem` still has `[JsonExtensionData] AdditionalProperties`). Options: (a) keep sending `available_online` / `available_for_pickup` / `available_electronically` through `CatalogItem.AdditionalProperties` — same wire JSON as 1.2.0, the pattern `CreatePaymentRequestExtensions` already uses for `integration_id`; whether Square still honours the fields is `UNVERIFIED`; the catalog test then reads the value from `ItemData.AdditionalProperties`; or (b) stop sending them — matches the 3.0.0 contract but drops behaviour, and the test's `AvailableOnline` assertion loses its subject. Recommended: (a). **Decision: (b)** — the 3.0.0 contract has no such members, so `SquareCatalogService.UpsertProductAsync` no longer sends them (`Published`/`IsDownload` are not sent); the catalog test asserts `ItemData.Name` instead of the removed `AvailableOnline`. Reported as a behaviour change.
- **A2 — Saved cards now come from `Cards.ListCards(CustomerId)`** because `Customer.Cards` was removed (its removal note in 1.2.0 source named ListCards as the replacement). `SquareCardService.GetSavedCardsAsync` stops calling `RetrieveCustomer`; it keeps the `Enabled != false` filter (harmless; default `IncludeDisabled=false`). Behaviour difference: an unknown customer id yields an empty list instead of a 404 exception (T8). `UNVERIFIED` whether `ListCards` returns the same card set `customer.cards` did for every account.
- **A3 — Currency/country codes not declared by the SDK enums.** `Money.Currency` / `Address.Country` need `Currency.TryGetKnownValue` / `Country.TryGetKnownValue` from nopCommerce string codes. Proposed: an undeclared currency → `NopException("The {code} currency is not supported by the Square")` (same message as today's `CheckSupportCurrency` failure); an undeclared country → `Country = null` (today's code already sends `null` for a code that fails `RegionInfo`). **Decision: as proposed**, implemented in `SquareCodes.ToCurrency` / `SquareCodes.ToCountry` (used by `SquarePaymentMethod`, `SquareCatalogService`, `LegacyTransactionService`).
- **A4 — String-typed enums in the plugin's own API stay strings.** `SquarePaymentDefaults.Status` constants, `SavedCardInfo`, `LegacyTenderBalance.Currency` (`string`), `CatalogProductInfo.Currency` (`string`), `LegacyTransactionService.RefundAsync` return (`PaymentRefund.Status`, still `string`) are plugin types — convert at the SDK boundary only (`.Value`, null-safe), no public signature change.
- **A5 — Two cross-operation checks the 1.2.0 code does not perform** (stored-card id ∈ customer's `ListCards`; inventory location ids ∈ `ListLocations`) are listed in §2.7 as the workflow requires. They add a read before the write. If the user wants strictly 1.2.0 behaviour, these are the two to drop; otherwise implement as written. **Decision: not added** — the task asks for behaviour kept the same; both checks are new behaviour outside the upgrade.
- **A6 — Production with an empty access token is not refused at startup** (pre-existing; per-store settings are only known per call). Not changed by the upgrade.
